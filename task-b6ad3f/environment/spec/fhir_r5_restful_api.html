3.2.0 RESTful API

This page is part of the FHIR Specification (v5.0.0: R5 – STU). This is the current published version.

FHIR is described as a ‘RESTful’ specification based on common industry level use of the term REST. In practice, FHIR only supports Level 2 of the REST Maturity model as part of the core specification, though full Level 3 conformance is possible through the use of extensions.

For each “resource type” the same set of interactions are defined which can be used to manage the resources in a highly granular fashion.

3.2.0.1 Defined Interactions

Instance Level Interactions
readRead the current state of the resource
vreadRead the state of a specific version of the resource
updateUpdate an existing resource by its id (or create it if it is new)
patchUpdate an existing resource by posting a set of changes to it
deleteDelete a resource
historyRetrieve the change history for a particular resource
Type Level Interactions
createCreate a new resource with a server assigned id
searchSearch the resource type based on some filter criteria
Whole System Interactions
capabilitiesGet a capability statement for the system
batch/transactionUpdate, create or delete a set of resources in a single interaction
historyRetrieve the change history for all resources

3.2.0.2 General Considerations

3.2.0.2.1 Content Types and encodings

The formal MIME-type for FHIR resources is application/fhir+json or application/fhir+xml. The correct mime type SHALL be used by clients and servers. Servers SHALL support JSON.

3.2.0.2.2 Resource Metadata and Versioning

Each resource has a set of metadata elements in the meta element. Version-aware servers track changes to resources and provide the versionId element. The version changes each time the resource changes, and the server populates it when the client does not provide it.

Version Management: When a server processes an update (PUT) to an existing resource, the meta.versionId SHALL be incremented (typically by 1) from the current version of the resource on the server. For newly created resources (POST), meta.versionId is set to "1". The meta.lastUpdated element SHALL be updated to reflect the time of the operation.

Note: the version id is a server-assigned value, and the client cannot predict its value. When comparing versions, the server SHOULD use string comparison.

3.2.0.2.3 Security

Communications SHALL be secured with TLS/SSL in production. For further information, see the Security Page.

3.2.0.3 read

The read interaction accesses the current contents of a resource. The interaction is performed by an HTTP GET command:

GET [base]/[type]/[id] {?_format=[mime-type]}

This returns a single instance with the content specified for the resource type. This url may be accessed by a browser. The possible response codes are:

CodeDescription
200Successfully retrieved the resource
404Resource not found for the given id
410Deleted resource

3.2.0.4 vread

The vread interaction accesses a specific version of a resource instance:

GET [base]/[type]/[id]/_history/[vid]

3.2.0.5 update

The update interaction creates a new current version for an existing resource, or creates an initial version if no resource already exists for the given id. The update interaction is performed by an HTTP PUT command:

PUT [base]/[type]/[id] {?_format=[mime-type]}

The request body SHALL be a Resource with an id element that has an identical value to the [id] in the URL. The server SHALL update the meta.versionId and meta.lastUpdated on the resource being stored.

CodeDescription
200Successfully updated (existing resource)
201Successfully created (new resource via upsert)
400Bad Request - resource could not be parsed or failed basic FHIR validation rules
404Resource type not supported, or not a FHIR end-point
405Not Allowed - the resource did not exist prior to the update, and the server does not allow client defined ids
409/412Version conflict management
422Proposed resource violated applicable FHIR profiles or server business rules

3.2.0.6 patch

As an alternative to updating an entire resource, clients can perform a patch operation using HTTP PATCH.

3.2.0.7 delete

The delete interaction removes an existing resource. The interaction is performed by an HTTP DELETE command:

DELETE [base]/[type]/[id]

A delete interaction means that subsequent non-version-specific read interactions will not result in the resource being found. Servers may choose to physically delete the resource, or mark it as inactive. For servers that don't support the delete interaction, the server should return a 405 Method Not Allowed status code.

CodeDescription
200OK – resource deleted, response includes an OperationOutcome
204No Content – resource successfully deleted, no response body
404Not Found – resource type or id not supported
405Method Not Allowed – delete not supported
409Conflict – cannot be deleted due to referential integrity

Note: The typical response code for a successful deletion without a returned body is 204 No Content. A server SHALL return a 200 OK only if it returns a payload (e.g., an OperationOutcome) describing the result. If no payload is returned, the server SHOULD use 204.

3.2.0.8 create

The create interaction creates a new resource in a server-assigned location. If the client wishes to have control over the id of a newly submitted resource, it should use the update interaction instead. The create interaction is performed by an HTTP POST command:

POST [base]/[type] {?_format=[mime-type]}

The request body SHALL be a FHIR Resource. The server ignores the resource id if one is provided and assigns a new one. The server SHALL populate meta.versionId and meta.lastUpdated.

CodeDescription
201Created – resource was successfully created on the server, with a Location header
400Bad Request
404Not Found – resource type not supported
405Method Not Allowed
422Unprocessable Entity – proposed resource violated applicable profiles

3.2.0.8.1 Conditional create

The conditional create interaction allows a client to create a new resource only if some equivalent resource does not already exist on the server. The client provides search parameters in the If-None-Exist header (or in the ifNoneExist field of a Bundle entry request):

POST [base]/[type]
If-None-Exist: [search parameters]

If no resources match, the server performs the create as above. If a single match is found, the server returns 200 OK and the existing resource. If multiple matches, the server returns 412 Precondition Failed.

3.2.0.9 search

This interaction searches a set of resources based on some filter criteria. Search functionality is described in detail on the Search page.

3.2.0.10 capabilities

The capabilities interaction retrieves the information about a server’s capabilities – which portions of this specification it supports:

GET [base]/metadata {?mode=[mode]} {&_format=[mime-type]}

3.2.0.11 batch/transaction

The batch and transaction interactions submit a set of actions to perform on a server in a single HTTP request/response. The actions may be performed independently as a “batch”, or as a single atomic “transaction” where the entire set of changes succeed or fail as a single entity. Multiple actions on multiple resources of the same or different types may be submitted, and they may be a mix of interactions defined on this page (e.g., read, search, create, update, delete) or operations (at the system, resource type, or instance level).

The transaction and batch interactions are performed by an HTTP POST command:

POST [base] {?_format=[mime-type]}

The content of the post submission is a Bundle with Bundle.type = batch or transaction. Each entry carries request details (Bundle.entry.request) that provide the HTTP verb, URL, and optional headers that together form the HTTP request the entry represents.

3.2.0.11.1 Processing Rules – Transaction

A transaction is a single atomic action. For a transaction, servers SHALL either accept all actions and return a 200 OK, along with a response bundle (see below), or reject all resources and return an HTTP 400 or 500 type response. Note that a transaction cannot be partially applied.

Processing Order: Because of the atomicity requirement, a server SHOULD process a transaction in the following order to avoid dependency issues:

  1. Process any DELETE interactions
  2. Process any POST interactions (creates)
  3. Process any PUT or PATCH interactions (updates)
  4. Process any GET or HEAD interactions (reads/searches)
  5. Resolve any conditional references

If any resource identities (including resolved identities from conditional update/delete) overlap in steps 1–3, then the transaction SHALL fail.

The outcome of processing the transaction SHALL NOT depend on the order of the resources in the transaction. A resource can only appear in a transaction once (by identity).

3.2.0.11.2 References in Transactions

Transactions may include references between entries where resources refer to each other. When the server assigns a new id to any resource in the transaction (i.e. in response to a POST/create), it SHALL also update any references to that resource in the same bundle as they are processed. References to resources that are not part of the transaction are left unchanged.

Reference Resolution – fullUrl Mapping:

  • For POST (create) entries, the fullUrl (typically a urn:uuid: or urn:oid: value) serves as the identity of the resource within the Bundle. The server ignores this value for the purpose of assigning a persistent id, but uses it to resolve references.
  • When processing a transaction, the server SHALL build a mapping of all fullUrl values for POST entries to their server-assigned identities ([type]/[id]) before resolving any references. This is necessary to support circular references between resources (e.g., resource A references resource B and resource B references resource A).
  • After the mapping is established, the server SHALL replace all matching urn:uuid: references throughout every resource in the transaction with the corresponding server-assigned reference. This replacement applies to all elements in the resource regardless of depth or position, including inside:
    • Standard reference elements (subject, encounter, etc.)
    • Extension elements (extension[].valueReference.reference)
    • Array elements (hasMember[].reference, derivedFrom[].reference, basedOn[].reference, etc.)
    • Any element of type uri, url, oid, or uuid
    • Narrative content (<a href=""> and <img src="">)
  • References to resources already existing on the server (e.g., Practitioner/pract-001) are not modified.

Implementation Note: A common implementation error is to only resolve references in “well-known” reference fields (such as subject and encounter). FHIR resources can contain references in any position, including within extensions, modifierExtensions, contained resources, and deeply nested array structures. Implementers SHOULD use a recursive traversal of the entire resource structure to find and resolve all urn:uuid: references, rather than enumerating individual field paths.

3.2.0.11.3 Identity Assignment

When a server processes a POST entry in a transaction, it assigns a new server-generated id. The fullUrl of the entry (if a urn:uuid:) is used only for cross-referencing within the bundle and is not stored as part of the resource.

For PUT entries, the request.url identifies the resource being updated. The resource id element in the body should match the id in the URL.

3.2.0.11.4 Conditional Operations in Transactions

Conditional creates (ifNoneExist), conditional updates, and conditional deletes can all be used inside transactions. The server resolves the condition as part of transaction processing. If the condition on a conditional create matches zero existing resources, the create proceeds normally.

3.2.0.11.4.1 Conditional References in Transactions

Resources within a transaction may contain conditional references — references of the form [Type]?[search parameters] (e.g., Patient?identifier=http://hospital.example.org/mrn|MRN-12345). These are distinct from urn:uuid: references and represent a search-based reference that must be resolved by the server during transaction processing.

Conditional Reference Resolution:

  • When processing a transaction, the server SHALL resolve any conditional references that appear in resource content by performing the implied search against the current server state (including any modifications made by prior steps of the transaction).
  • If the search resolves to exactly one resource, the conditional reference SHALL be replaced with a direct reference to that resource (e.g., Patient/pat-001).
  • If zero matches are found, the transaction SHALL fail with a 412 Precondition Failed error.
  • If multiple matches are found, the transaction SHALL fail with a 412 Precondition Failed error.
  • For token search parameters (such as identifier), the search value uses the format [system]|[value]. Both system and value must match for a successful resolution.

Implementation Note: Conditional references can appear alongside urn:uuid: references in the same resource. For example, a ServiceRequest might have its subject as a conditional reference (Patient?identifier=...) while its encounter uses a urn:uuid: reference to another entry in the same transaction. Implementers must handle both reference types during transaction processing.

3.2.0.11.4.2 Conditional Create and Reference Mapping

When a conditional create (ifNoneExist) matches an existing resource and the create is therefore skipped, the server MUST handle the entry’s fullUrl for reference resolution purposes:

  • If the conditional create entry has a fullUrl (e.g., urn:uuid:...), that fullUrl SHALL be mapped to the existing matched resource’s server identity (e.g., AllergyIntolerance/allergy-001) in the reference resolution mapping.
  • This ensures that other entries in the same transaction that reference the conditional create’s fullUrl will correctly resolve to the existing matched resource.
  • The response entry for a matched conditional create SHALL have status 200 OK (not 201 Created), since no new resource was created.
  • Failure to map the fullUrl of a skipped conditional create will result in unresolved urn:uuid: references in other transaction entries that depend on the conditional create’s identity, which constitutes a conformance violation.

3.2.0.11.5 Transaction/Batch Response

For a successful transaction or batch, the server SHALL return a Bundle with type = transaction-response or batch-response. The response Bundle contains one entry for each entry in the request, in the same order. Each entry SHALL contain a response element which details:

  • The HTTP status code as a string (e.g., "201 Created", "200 OK", "204 No Content")
  • The location header value, where applicable (for creates)
  • The etag header value (for versioned resources)
  • The lastModified timestamp

Status Codes in Transaction Responses: The status code for each entry in the response bundle should reflect the result of the individual operation within the transaction:

OperationSuccess CodeNotes
DELETE204 No ContentResource was deleted; no response body for this entry. Do not use 200 unless an OperationOutcome is returned.
POST (create)201 CreatedNew resource created; location header SHOULD be populated
PUT (update existing)200 OKExisting resource updated
PUT (create via upsert)201 CreatedNew resource created at client-specified id
GET (read/search)200 OKResource or search results returned

For a failed transaction, the server does NOT return a Bundle. Instead, it returns a single OperationOutcome resource with an HTTP status code in the 4xx or 5xx range.

3.2.0.11.6 Processing Rules – Batch

In a batch, there is no expectation of atomicity. Each entry is treated as an independent interaction. There SHALL be no interdependencies between different entries in a batch. The server processes each entry independently and returns a response for each.

In contrast to transactions, references between entries in a batch that use urn:uuid: are considered non-conformant.

3.2.0.12 history

The history interaction retrieves the history of either a particular resource, all resources of a given type, or all resources supported by the system:

GET [base]/[type]/[id]/_history{?[parameters]&_format=[mime-type]}
GET [base]/[type]/_history{?[parameters]&_format=[mime-type]}
GET [base]/_history{?[parameters]&_format=[mime-type]}

3.2.0.14 Extensions and Data Types in RESTful Interactions

FHIR allows resources to include extensions that carry additional data not defined in the base resource. Extensions use the extension element which contains:

  • url – identifies the meaning of the extension
  • A value element chosen from the set of FHIR data types: valueString, valueBoolean, valueInteger, valueReference, valueCodeableConcept, etc.

When an extension uses valueReference, it contains a standard FHIR Reference data type with a reference element. These references are subject to the same resolution rules as any other reference in the resource. During transaction processing, urn:uuid: references inside extensions MUST be resolved just like top-level references.

Common Pitfall: Extension-carried references are frequently overlooked during transaction reference resolution because they do not appear at predictable positions in the resource structure. Implementers must ensure their reference resolution logic traverses the complete resource tree, including all extensions at every level.

3.2.0.15 Bundle Resource

A Bundle resource is a container for a collection of resources. Bundles are used in many contexts in FHIR:

  • Returning search results (searchset)
  • Sending a set of actions (transaction / batch)
  • Communicating a group of resources as part of a message (message)
  • Grouping a self-contained set of resources to act as an exchangeable document (document)

For transaction bundles, each entry element contains:

  • fullUrl – the identity of the resource for referencing within the bundle
  • resource – the resource content
  • request – HTTP request details: method, url, and optionally ifNoneMatch, ifModifiedSince, ifMatch, ifNoneExist

For transaction-response bundles, each entry contains:

  • response – the outcome: status, location, etag, lastModified, and optionally outcome
  • Optionally resource – the resource as stored (controlled by Prefer header)
