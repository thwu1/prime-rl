# MeshLink Protocol (MLP) Specification v1.0

## Overview

MeshLink Protocol (MLP) is a lightweight binary protocol for mesh network
communication. Each message is encapsulated in a self-describing packet with
integrity checking.

## Packet Format

Every MLP packet consists of a fixed 8-byte header followed by a variable-length
payload.

```
Offset  Size  Field
------  ----  -----
0       2     Magic bytes: 0x4D 0x4C ("ML")
2       1     Version (current: 1)
3       1     Message type (0-5, see below)
4       2     Payload length (big-endian uint16)
6       2     CRC-16 checksum (big-endian uint16)
8       N     Payload (N = payload length)
```

### Checksum

The CRC-16 uses the CCITT polynomial (0x1021) with an initial value of 0xFFFF.
It is computed over the non-magic, non-CRC header fields concatenated with the
payload bytes.

## Message Types

### Type 0: HELLO

Announces a node on the network.

| Offset | Size | Field |
|--------|------|-------|
| 0 | 4 | Node ID (big-endian uint32) |
| 4 | variable | Node name (null-terminated UTF-8 string) |

### Type 1: DATA

Carries application data on a numbered channel.

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | Channel ID |
| 1 | 4 | Sequence number (big-endian uint32) |
| 5 | variable | Data payload |

### Type 2: ACK

Acknowledges receipt of a DATA message.

| Offset | Size | Field |
|--------|------|-------|
| 0 | 4 | Sequence number (big-endian uint32) |

### Type 3: ERROR

Reports an error condition.

| Offset | Size | Field |
|--------|------|-------|
| 0 | 2 | Error code (big-endian uint16) |
| 2 | variable | Error message (UTF-8, NOT null-terminated; length from header) |

### Type 4: ROUTE

Describes a routing path through the mesh.

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | Hop count |
| 1 | variable | Route path: sequence of 4-byte big-endian node IDs |

### Type 5: FRAGMENT

A fragment of a larger message that has been split for transmission.

| Offset | Size | Field |
|--------|------|-------|
| 0 | 4 | Message ID (big-endian uint32) |
| 4 | 2 | Fragment index (big-endian uint16, 0-based) |
| 6 | 2 | Total fragments (big-endian uint16) |
| 8 | variable | Fragment data |

## Secure Channels

DATA packets transmitted on channels 128-255 (channels with bit 7 set) use
payload scrambling to provide basic confidentiality. The data portion of the
payload is transformed using a keystream generated by a seeded bitwise
recurrence relation derived from packet header fields. Each data byte is XOR'd
with the corresponding byte of this keystream. The generator state advances once
per output byte, and the keystream byte is extracted from the low bits of the
current state.

*Note: The keystream generator algorithm, its characteristic polynomial, seed
derivation, and zero-seed edge case handling are implementation-defined and not
part of this specification. Refer to the reference implementation for the
algorithm details. The CRC checksum covers the scrambled (on-wire) payload
bytes, not the cleartext.*

## Tool Usage

The `pktool-ref` command-line tool reads MLP packet data from binary files.

```
pktool-ref decode <file>       Decode and display packets
pktool-ref validate <file>     Validate packet integrity
pktool-ref stats <file>        Show aggregate statistics
pktool-ref filter <expr> <file>  Filter packets by field values
pktool-ref reassemble <file>   Reassemble fragmented messages
```

### Decode Example

```
$ pktool-ref decode samples/mixed.bin
Packet #1:
  Type: HELLO (0)
  Node ID: 0x00000001
  Node Name: "gateway"

Packet #2:
  Type: DATA (1)
  Channel: 1
  Sequence: 100
  Data: 48656c6c6f2c204d6573684c696e6b21 (16 bytes)
  ...
```

### Filter Expressions

Comma-separated `key=value` pairs. Supported keys include `type`, `channel`,
`seq`, `node_id`, `error_code`, `msg_id`, `hop_count`. Multiple pairs combine
with AND logic.

```
pktool-ref filter "type=DATA" file.bin
pktool-ref filter "type=DATA,channel=1" file.bin
```

### Reassemble

The `reassemble` command collects FRAGMENT packets from the input file, groups
them by Message ID, and reports the reassembly status of each message. Messages
are reported in ascending Message ID order. Complete messages include the
concatenated payload; incomplete messages identify which fragments are absent.
