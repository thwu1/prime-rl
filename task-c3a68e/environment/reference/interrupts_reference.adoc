= Interrupts
(Excerpted from Hubris RTOS reference documentation)

This chapter discusses the role of CPU interrupts in Hubris applications.

== Interrupts vs Exceptions

An _interrupt_ is generated by a peripheral to signal an asynchronous event.
Drivers usually want to find out about some set of interrupts and react to them.

An _exception_ is a broader idea that includes signals generated by the
processor in response to the program's behavior (memory access violations,
illegal instructions, etc.).

The kernel provides first-line handlers for all exceptions, interrupts included,
but will route _interrupts_ to application tasks.

== Interrupts from a task's perspective

The `app.toml` configuration file can route interrupts to tasks, by binding
platform interrupt numbers to _notification bits._ From the task's perspective,
interrupts are delivered as notifications (see the IPC chapter).

Hubris does not allow a single interrupt to be routed to multiple tasks, which
means that a task has exclusive control over any interrupts it handles.

When a task starts (or restarts) its interrupts are initially masked. The task
uses `irq_control` to unmask a subset of its interrupts. When calling
`irq_control`, the task names its interrupts by the notification bits they will
set when they fire, rather than their hardware interrupt numbers.

== Interrupt-to-notification binding

In `app.toml`, a task's `interrupts` table maps hardware IRQ names to
notification names. When the interrupt fires, the kernel posts the
corresponding notification bit to the task.

For this binding to be valid, the notification name referenced in the
`interrupts` table must appear in the task's `notifications` list — otherwise
the kernel would not know which bit to post, and the task would have no way
to detect the interrupt.

The interrupt routing information is baked into the kernel at compile time.
The kernel stores, for each implemented interrupt, the index of the handling
task and the notification set to post.

== Routing interrupts to tasks in the kernel

When an interrupt happens, it gets routed to a generic kernel ISR. The kernel
ISR will find the task named in the response record, and post the notification
set. The kernel then clears the interrupt's `enable` bit to prevent reoccurrence
until the task has a chance to respond.

As with any situation where the kernel posts notifications, the kernel exit path
then checks to see if the notification has caused the scheduling situation to
change — if the task handling the interrupt is higher priority than whatever
task was running before, the kernel saves context for the interrupted task and
switches to the handler task.
